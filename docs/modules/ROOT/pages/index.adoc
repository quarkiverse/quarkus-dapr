= Quarkus - Dapr
:extension-status: preview

include::./includes/attributes.adoc[]

A Quarkus extension that lets you build applications on top of the https://dapr.io/[Dapr] distributed application runtime.

== Installation

If you want to use this extension, you need to add the `io.quarkiverse.dapr:quarkus-dapr` extension first to your build file.

For instance, with Maven, add the following dependency to your POM file:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.quarkiverse.dapr</groupId>
    <artifactId>quarkus-dapr</artifactId>
    <version>{project-version}</version>
</dependency>
----

== Introduction

=== What is Dapr?

Dapr is a portable, event-driven runtime that makes it easy for any developer to build resilient, stateless and
stateful applications that run on the cloud and edge and embraces the diversity of languages and developer frameworks.

Leveraging the benefits of a sidecar architecture, Dapr helps you tackle the challenges that come with building
microservices and keeps your code platform agnostic.

For more information about Dapr, please go https://dapr.io/.

===  What is Quarkus-Dapr?

Quarkus Dapr is a Quarkus extension to integrate with Dapr.

Quarkus Dapr Extension enables Java developers to create ultra lightweight Java native applications for Function
Computing and FaaS scenes, which is also particularly suitable for running as serverless.

With the help of Dapr, these ultra lightweight Java native applications can easily interact with external application
and resources. Dapr provides many useful building blocks to build modern distributed application: service invocation,
state management, input/output bindings, publish & subscribe, secret management......

Because of the advantages of sidecar model, the native applications can benefit from Dapr's distributed capabilities
while remain lightweight without introducing too many dependencies. This is not only helping to keep the size of java
native applications, but also making the native applications easy to build as native images.

== Examples

With Quarkus Dapr Extension, it's pretty easy for java developers.

=== publish & subscribe

To publish events to your message broker, just inject a dapr client to your bean and call it's publishEvent() method:

[source,java]
----
@Inject
SyncDaprClient dapr;

dapr.publishEvent("messagebus", "topic1", "Hello from Quarkus!");
----

To subscribe events for your message broker, adding some annotations on your method is enough.
Dapr delivers each event wrapped in a https://cloudevents.io/[CloudEvent] envelope. Declare the method parameter
as `io.dapr.client.domain.CloudEvent<T>`, where `T` is the type of the event payload, to get access to the envelope:

[source,java]
----
@POST
@Path("/topic1")
@Topic(name = "topic1", pubsubName = "messagebus")
public void eventOnTopic1(CloudEvent<String> event) {
    String content = event.getData();
    // ...
}
----

This extension supports `CloudEvent` as the event type, with any payload type:

[source,java]
----
@POST
@Path("/topic2")
@Topic(name = "topic2", pubsubName = "messagebus")
public void eventOnTopic2(CloudEvent<MyData> event) {
    MyData data = event.getData();
    // ...
}
----

The parameter can also be a custom type, which is deserialized from the event data:

[source,java]
----
@POST
@Path("/topic3")
@Topic(name = "topic3", pubsubName = "messagebus")
public void eventOnTopic3(MyData data) {
    // ...
}
----

In the attributes `name`, `pubsubName`, and `match` of the `@Topic` annotation, it is possible to set a config property to be loaded at runtime.

[source,java]
----
@POST
@Path("/topic6")
@Topic(name = "${topic6}", pubsubName = "${pubsub.topic6}", rule = @Rule(match = "${match.rule6}", priority = 1))
public void eventOnTopic6(CloudEvent<String> event) {
    // ...
}
----

=== service invocation

Instead of calling `DaprClient#invokeMethod` directly, you can declare an interface annotated with `@RegisterDaprInvokeClient`
and inject it with the `@DaprInvokeClient` qualifier (`@Inject` is optional):

[source,java]
----
@Path("/orders")
@RegisterDaprInvokeClient(appId = "order-service")
public interface OrderService {

    @GET
    @Path("/{id}")
    Order getById(@PathParam("id") String id, @QueryParam("expand") String expand);

    @POST
    Uni<Order> create(Order order);
}

@ApplicationScoped
public class OrderResource {

    @DaprInvokeClient
    OrderService orderService;
}
----

The interface is a regular https://quarkus.io/guides/rest-client[Quarkus REST Client] (as if it was annotated with `@RegisterRestClient`),
so everything the REST Client supports is available: Jakarta REST annotations, `Uni<T>` and `CompletionStage<T>` return types,
providers, exception mappers, etc. The differences are:

* the requests are sent to the Dapr sidecar (`DAPR_HTTP_ENDPOINT`, or `DAPR_SIDECAR_IP` and `DAPR_HTTP_PORT`) instead of a configured URL;
* the `dapr-app-id` header is set to the `appId` attribute, so the sidecar routes the request to the target application;
* the `dapr-api-token` header is sent when `DAPR_API_TOKEN` is set;
* the client is injected with `@DaprInvokeClient` instead of `@RestClient`.

The client can be tuned with the REST Client configuration, using the fully qualified name of the interface as the key,
e.g. `quarkus.rest-client."org.acme.OrderService".read-timeout=5000`.

The `appId` attribute can reference a config property, e.g. `@RegisterDaprInvokeClient(appId = "${order-service.app-id}")`.

For more details and hands-on experiences, please reference to our link:https://github.com/quarkiverse/quarkus-dapr/blob/main/demo/README.md[Demo].
